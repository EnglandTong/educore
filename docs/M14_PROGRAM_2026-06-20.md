# M14 Program - MVP Readiness Hardening

Status: Active
Owner: MRT-Controller-QA
Created: 2026-06-20T08:49:58+08:00

## Milestone Goal

Make the signed local acceptance candidate more reproducible, reviewable, and ready for MVP handoff by hardening evidence, extending verification depth for the existing student loop, and documenting deployment prechecks without production access.

## Program Scope

- Harden the existing strict acceptance script and evidence notes.
- Add or improve local verification depth for the existing student training loop.
- Document deployment precheck requirements using non-secret, non-production guidance.
- Clean up current loop-control documentation enough that Developer execution is unambiguous.

## Non-Goals

- New product architecture, new subsystem, or new shared platform layer.
- Production deployment, production configuration, or production credential handling.
- Broad UI redesign, new feature work, or unrelated refactors.
- Dependency installation or network-based remediation.
- Destructive git operations or rewriting evidence history.

## Work Order Sequence

1. `P14-01` - Acceptance script and evidence asset hardening. Complexity: `Standard`.
2. `P14-02` - Student training loop e2e verification depth. Complexity: `Standard`.
3. `P14-03` - Deployment precheck documentation. Complexity: `Standard`.
4. `P14-04` - Program evidence consolidation and docs readability pass. Complexity: `Lite`.

## Dependencies

- `P14-02` depends on `P14-01` because e2e evidence must rely on trustworthy strict acceptance behavior.
- `P14-03` depends on `P14-01` because deployment precheck documentation must reference stable local acceptance evidence.
- `P14-04` depends on `P14-01`, `P14-02`, and `P14-03` because it consolidates the program handoff.

## Developer Auto-Advance Rules

Developer may proceed from one work order to the next only when all conditions are true:

- The current work order acceptance criteria pass.
- Required verification commands were run or a documented no-run reason is allowed by the work order.
- Evidence and handoff updates are written to `docs/STATUS.md`, `docs/PENDING.md`, `docs/COMPLETED.md`, and applicable loop/evidence files.
- No `docs/STOP_RULES.md` condition is triggered.
- No change outside the work order allowed files is required.
- The same verification failure has not occurred three consecutive times for the same unresolved reason.

Developer may mark each work order as `Developer Complete` or `Ready for Controller/QA Review` only. Developer must not mark the milestone as `Accepted` or `Completed`.

## Mandatory Stop Conditions

Developer must stop and return to Controller/QA or Owner if any condition occurs:

- Production secrets, production credentials, private keys, or live user data are required.
- Any write outside `D:\Development\EduCore` is required.
- A new architecture, new subsystem, or shared layer is needed.
- A product code fix outside an active work order's allowed files is required.
- A dependency install or external network call is needed.
- A destructive git operation is needed.
- Evidence history would need to be deleted or rewritten instead of appended.
- The same command fails three consecutive times for the same unresolved reason.

## Program Verification Baseline

- `powershell -ExecutionPolicy Bypass -File .\agent-loop-check.ps1 -SkipInstall -Strict`
- `corepack pnpm --filter @educore/web run test:e2e --reporter=list`

## Expected Final Developer Handoff

At the end of `P14-04`, Developer must create a consolidated M14 handoff in `docs/STATUS.md` or a linked evidence file with:

- Work orders completed.
- Exact timestamps in Asia/Shanghai time.
- Exact commands and results.
- Evidence paths.
- Remaining risks or `None`.
- Confirmation that the Program stayed within `docs/TARGET.md` and did not trigger `docs/STOP_RULES.md`.
