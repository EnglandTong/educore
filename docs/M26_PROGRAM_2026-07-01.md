# M26 Program - EduCore Product Baseline Re-engagement

Program ID: M26  
Date: 2026-07-01  
Owner: MRT-Controller-QA  
Status: Staged / Ready for Dispatch  
Associated Milestone: `Docs/MILESTONE_M26_EDUCORE_PRODUCT_BASELINE_REENGAGEMENT_2026-07-01.md`

---

## 1. Program Goal

Transition the project from governance-only cycles back toward product-facing work by conducting a bounded, read-only audit and planning exercise. Assess the current EduCore codebase state, identify feature gaps against the Core Target, and define the minimum deliverable slice for the next product milestone.

## 2. Program Scope

- Audit the current state of all EduCore product directories.
- Map existing implementation against `Docs/TARGET.md` Core Target.
- Identify completed, partial, and missing features.
- Define a bounded minimum product slice for the next milestone.
- Produce a consolidated Program handoff with recommendations.

## 3. Non-Goals

- No product code implementation or modification.
- No new architecture, subsystem, or shared layer.
- No production deployment or credential access.
- No destructive operations.
- No changes outside `D:\Development\EduCore`.
- No modification of `TARGET.md` Core Target or `STOP_RULES.md`.

## 4. Work Order Sequence

| Order | ID | Complexity | Task | Predecessor |
|---|---|---|---|---|
| 1 | P26-01 | Lite | EduCore codebase state audit | none |
| 2 | P26-02 | Standard | Feature gap analysis against Core Target | P26-01 |
| 3 | P26-03 | Standard | Minimum deliverable product slice definition | P26-02 |
| 4 | P26-04 | Standard | Consolidated milestone handoff and product readiness assessment | P26-03 |

## 5. Dependency Rules

- P26-01 must be verified and handed off before P26-02 begins.
- P26-02 must be verified and handed off before P26-03 begins.
- P26-03 must be verified and handed off before P26-04 begins.

Developer may auto-advance to the next Work Order in this Program provided:
- The previous Work Order has a handoff with evidence.
- No stop rule is triggered.
- No verification command failed.
- No scope conflict is detected.

## 6. Complexity Definitions

- **Lite**: Single verification command, file existence check, or read-only audit. Low risk. Developer may close with evidence.
- **Standard**: Multi-step verification, cross-file analysis, or documentation update requiring handoff and Controller/QA review.
- **Deep**: Extensive audit, architecture review, or multi-system validation. Requires Controller/QA signoff per sub-step.

- `Docs/STOP_RULES.md`
- `Docs/ACCEPTANCE.md`
- `Docs/RUBRIC.md`
- Any file outside `D:\Development\EduCore`.
- Developer must NOT modify any product implementation files under `apps/`, `packages/`, `shared/`, `MarketSurvey/`, `TradeData/`, `Hub/`.

## 9. Stop Conditions

- Triggering any item in `Docs/STOP_RULES.md`.
- Missing required directory that cannot be located.
- Three consecutive failures of the same verification command for the same unresolved reason.
- Detection of unauthorized file modifications outside the Allowed Files list.

## 10. Acceptance Criteria

- [ ] All four Work Orders have Developer handoff with evidence paths and verification results.
- [ ] Codebase audit documents the current state of all major product directories.
- [ ] Feature gap analysis identifies at least three specific items against TARGET.md.
- [ ] Minimum deliverable slice is bounded and does not require new architecture.
- [ ] `Docs/HANDOFF_M26_PROGRAM_DEVELOPER.md` exists and references all Work Orders.
- [ ] No STOP_RULES triggered during Program execution.

```powershell
# Verify consolidated handoff exists

# Verify status files reference M26 and P26 work orders

```
