# M22 Program - Post-Recovery Evidence Ledger Stabilization

Date: 2026-06-29
Owner: MRT-Controller-QA
Status: Dispatched

## Milestone Goal

Stabilize the post-M21 evidence ledger and controller/developer state chain so the accepted M21 recovery outcome is easy to audit before the next bounded milestone is planned.

## Program Scope

- Docs-only evidence ledger stabilization.
- Roadmap, status, queue, and role-state coherence after M21 acceptance.
- Consolidated Developer handoff for M22.

## Non-Goals

- Product feature work.
- Product source changes.
- UI/UX behavior or copy changes.
- Backend, deployment, dependency, production, or external-service changes.
- Architecture, subsystem, or shared-layer changes.
- Changes to `docs/ACCEPTANCE.md`, `docs/STOP_RULES.md`, or acceptance pass conditions.
- Deleting, rewriting, or weakening historical evidence.

## Work Order Execution Order

1. `P22-01` - Post-recovery evidence ledger. Complexity: `Standard`.
2. `P22-02` - State, roadmap, and queue synchronization. Complexity: `Standard`.
3. `P22-03` - Consolidated M22 handoff and review publication. Complexity: `Standard`.

## Dependencies

- `P22-02` depends on `P22-01` because state files must reference the new evidence ledger.
- `P22-03` depends on `P22-02` because the final handoff must summarize the completed M22 state.

## Auto-Advance Rules

Developer may automatically continue to the next listed work order when:

- the previous work order is complete;
- the previous work order verification commands pass;
- evidence and handoff notes are written;
- changes remain within allowed files;
- no `docs/STOP_RULES.md` condition is triggered;
- no verification command fails three consecutive times for the same unresolved reason.

Developer must stop and return to Controller/QA or Owner when:

- a stop rule is triggered;
- the task requires product code, architecture, subsystem, shared-layer, deployment, or external-service changes;
- evidence conflicts with the accepted M21 recovery record;
- required evidence cannot be reconstructed from existing project files;
- credentials, production data, network provisioning, or out-of-repo writes are required.

## Final Program Handoff Requirement

At program end, Developer must leave:

- `docs/EVIDENCE_LEDGER_M22.md`
- `docs/HANDOFF_M22_PROGRAM_DEVELOPER.md`
- per-work-order handoff notes in `docs/LOOP_RUNS.jsonl`
- status updates in `docs/STATUS.md`, `docs/NEXT_ACTIONS.md`, `docs/PENDING.md`, and `docs/CURRENT_ROLE_INSTRUCTIONS.md`

Final Developer state must be `Ready for Controller/QA Review` or `Blocked`. Developer must not mark M22 as `Accepted` or `Completed`.
