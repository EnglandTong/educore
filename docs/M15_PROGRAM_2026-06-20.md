# M15 Program - Release Candidate Evidence Pack

Status: Active
Owner: MRT-Controller-QA
Created: 2026-06-20T10:03:37+08:00

## Milestone Goal

Make the local release-candidate evidence set easy to review, rerun, and hand off by mapping acceptance criteria to concrete evidence, documenting the smoke-flow procedure, auditing evidence freshness, and consolidating the Program handoff.

## Program Scope

- Build an acceptance evidence index from existing acceptance criteria and current evidence.
- Document a local smoke-flow checklist that stays within existing app behavior and local verification.
- Audit whether required evidence paths and timestamps are current and traceable.
- Consolidate final M15 Developer handoff for Controller/QA.

## Non-Goals

- New application features.
- New architecture, new subsystem, or shared platform layer.
- Production deployment, production configuration, or production credential handling.
- External services, network provisioning, dependency installation, or paid provider setup.
- Modifying `.env`, `.env.*`, production data, or secrets.
- Destructive git operations or rewriting evidence history.

## Work Order Sequence

1. `P15-01` - Acceptance evidence index. Complexity: `Standard`.
2. `P15-02` - Local smoke-flow checklist. Complexity: `Standard`.
3. `P15-03` - Evidence freshness audit. Complexity: `Standard`.
4. `P15-04` - Program handoff consolidation. Complexity: `Lite`.

## Dependencies

- `P15-02` depends on `P15-01` because the smoke-flow checklist should reference the evidence index.
- `P15-03` depends on `P15-01` and `P15-02` because it audits the evidence paths and checklist outputs.
- `P15-04` depends on `P15-01`, `P15-02`, and `P15-03` because it consolidates the final handoff.

## Developer Auto-Advance Rules

Developer may proceed from one work order to the next only when all conditions are true:

- The current work order acceptance criteria pass.
- Required verification commands were run or an allowed no-run reason is documented.
- Evidence and handoff updates are written to `docs/STATUS.md`, `docs/PENDING.md`, `docs/COMPLETED.md`, and `docs/LOOP_RUNS.jsonl`.
- No `docs/STOP_RULES.md` condition is triggered.
- No change outside the current work order allowed files is required.
- The same verification failure has not occurred three consecutive times for the same unresolved reason.

Developer may mark each work order as `Developer Complete` or `Ready for Controller/QA Review` only. Developer must not mark M15 as `Accepted` or `Completed`.

## Mandatory Stop Conditions

Developer must stop and return to Controller/QA or Owner if any condition occurs:

- Production secrets, production credentials, private keys, OAuth tokens, paid-service keys, or live user data are required.
- Any write outside `D:\Development\EduCore` is required.
- A new architecture, new subsystem, shared layer, deployment script, or product feature is needed.
- A product code fix outside an active work order's allowed files is required.
- Dependency installation or external network access is required.
- A destructive git operation is required.
- Evidence history would need to be deleted or rewritten instead of appended.
- The same command fails three consecutive times for the same unresolved reason.

## Program Verification Baseline

- `powershell -ExecutionPolicy Bypass -File .\agent-loop-check.ps1 -SkipInstall -Strict`
- `corepack pnpm --filter @educore/web run test:e2e --reporter=list`

## Expected Final Developer Handoff

At the end of `P15-04`, Developer must create a consolidated M15 handoff with:

- Work orders completed.
- Exact timestamps in Asia/Shanghai time.
- Exact commands and results.
- Evidence paths.
- Skipped checks and reasons, or `None`.
- Remaining risks or `None`.
- Confirmation that the Program stayed within `docs/TARGET.md` and did not trigger `docs/STOP_RULES.md`.
